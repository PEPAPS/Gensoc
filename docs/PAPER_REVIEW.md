# GenSoC — a written review

**Paper:** GenSoC: A Multi-Agent-Assisted SoC Generation Methodology Leveraging Open-Source Hardware
**Authors:** Peiran Yan, Qinzhe Zhi, Lifeng Liu, Tianyu Jia (Peking University)
**Venue:** 2025 IEEE/ACM International Symposium on Low Power Electronics and Design (ISLPED)
**DOI:** 10.1109/ISLPED65674.2025.11261756

This is the standalone written companion to the interactive site. It uses the same four provenance
labels, and the same rule: where the paper is silent, this document says so rather than guessing.

- **[FROM PAPER]** — the paper states this
- **[BACKGROUND]** — domain knowledge added here, not a claim about GenSoC
- **[INFERENCE]** — this review's reading, not stated outright by the paper
- **[NOT SPECIFIED]** — a question the paper leaves open

---

## 1. Summary

GenSoC is a methodology for generating a System-on-Chip from a natural-language request, using three
LLM agents that pass artifacts along a chain: an **IP Library Manager** that curates a structured
library of open-source hardware and selects blocks; a **SoC Integrator** that chooses bus protocols,
generates adapters, allocates addresses and emits integration documentation; and a **SoC Validator**
that compiles a test program, simulates the design, and repairs it in a loop.

The framework is built on MetaGPT with DeepSeek-Reasoner behind each agent. Two SoCs were generated
and carried through synthesis and place-and-route in TSMC 22 nm.

**[FROM PAPER]** The reported results: up to 27.18× and 29.67× lower normalized energy cost than SoCs
generated by LiteX for the two cases; up to 2.27× and 2.79× better energy efficiency than
area-matched homogeneous PULP Snitch baselines; and >24× faster than three graduate students
performing the same integration and verification manually.

---

## 2. The problem

**[FROM PAPER]** Two pressures. SoC architectures integrate increasingly many heterogeneous dedicated
accelerators, and conventional SoC design involves multiple time-consuming, labour-intensive phases.
Open-source hardware could supply the blocks, but existing IPs are organised in different
documentation formats and language styles — HDL or HLS — which makes them hard to understand and
reuse. Integrating new IPs into existing SoC platforms is inherently error-prone and requires
substantial time and effort.

**[FROM PAPER]** Existing platforms (Chipyard, LiteX, ESP, PULP) exist but the paper argues they have
limitations of IP scarcity and insufficient scalability.

**[INFERENCE]** There is a category difference here worth naming. Chipyard and LiteX are *generator*
frameworks: a block is supported because somebody wrote a generator for it, and that upfront work is
what makes their output reliable. GenSoC's proposal is that an agent can do that integration work per
design instead — trading guaranteed correctness for reach. Whether the trade pays depends entirely on
how often the verification loop converges, which the paper does not report.

## 3. Method

### 3.1 Agent 1 — IP Library Manager (Section IV-A)

**[FROM PAPER]** The manager refines — reorganises to a unified style — existing OSH code and
documentation using online resources and its expertise, then stores the refined materials in the
library. More than 90 OSH IPs were retrieved and reorganised.

Each IP is abstracted through a tree structure, where each node is a module's design code and
documentation and each edge is the hierarchy between modules. Descriptions exist at three levels:

| Level | Contents |
|---|---|
| **IP level** | Functional overview, technical parameters, benchmark performance metrics, typical application scenarios, PPA analysis |
| **Module level** | Module overview, configurable parameter lists, interface signal specifications, data flow, control flow |
| **Code level** | Code structure reorganisation, code refinement, added critical annotations |

**Table I — representative IPs**

| Category | Count | Named in Table I |
|---|---:|---|
| CPU | 23 | Xiangshan, OpenC910, CVA6, Rocket |
| GPU | 12 | Ventus, MIAOW, Nyuzi, Vortex |
| NPU | 10 | VTA, NVDLA, Gemmini, systolic-array |
| DSA | 16 | xk265, DSP, Crypto-Accelerator |
| I/O | 32 | GPIO, UART, SPI, DDR-controller |

**[FROM PAPER]** Selection runs as a reasoning process in tabular format, on both hard and soft
constraints. Hard constraints eliminate; soft constraints use a tiered evaluation with candidates
graded A/B/C.

**[INFERENCE]** The three-level scheme and the hierarchical RAG are two halves of one design.
Retrieval by type only works if something type-shaped exists to retrieve, which is what the IP-level
description provides. The library structure is an index built for a retrieval strategy, not
documentation written for humans.

**[NOT SPECIFIED]** The agent's guidelines and prompts; whether refinement was fully automated or
partly human-supervised; whether the refined library is publicly released; the design plan's format.

### 3.2 Agent 2 — SoC Integrator (Section IV-B)

**[FROM PAPER]** A protocol-driven integration method in three steps:

1. **Protocol selection.** Choose the protocol appropriate to the IP's characteristics. APB suits
   low-bandwidth peripherals; AXI is preferred for high-bandwidth scenarios such as CPU-accelerator
   interactions.
2. **Information extraction.** From the AMBA manual, extract protocol overviews, signal tables, read
   and write state-machine transition tables, and signal dependencies. The transition table defines
   current state, trigger signals and next state. Two dependency examples are given: ARVALID must
   precede RVALID; ARREADY is related to ARVALID but not strictly required to follow it.
3. **Adapter generation.** Reuse a configurable adapter where one fits — the paper names `axi
   adapter` (bit-width adaptation), `axi fifo` and `axi axilite` (protocol conversion). If no
   suitable adapter exists for an IP, the integrator writes a new one.

**[FROM PAPER]** After integration the agent scans all source IP code, modifies address-allocation
code, assigns memory address spaces, and generates three documents: the address mapping table
(hierarchical, detailing each IP's addresses), the register functional documentation (register
functions and their addresses), and the testpoint documentation (the IP features to be tested,
focused primarily on integration connectivity).

**[INFERENCE]** The strictness distinction in the dependency rules is more important than it looks. A
checker treating every observed ordering as mandatory would report false failures constantly, so
encoding which dependencies are strict is what makes the later comparison usable. The paper gives two
examples but does not publish the rule set.

**[INFERENCE]** The testpoint document quietly scopes verification to *integration connectivity*
rather than to each IP's internal function. That is a defensible scope for an integration tool, and
narrower than "the SoC is verified".

**[NOT SPECIFIED]** Adapter internal architecture; the full template set; how address conflicts are
detected; any generated RTL.

### 3.3 Agent 3 — SoC Validator (Section IV-C)

**[FROM PAPER]** Test code is compiled to binary and loaded into the RAM model; the simulator is
invoked to drive the peripherals; the simulation report is analysed to modify the source; the process
iterates within the testbench until all tests complete successfully.

**[FROM PAPER]** The motivation for the paper's verification contribution: *while LLMs excel in
handling code logic, they still have limitations in managing state machine signal triggers.* The
**state-machine signal comparison method** addresses this. It extracts key simulation data into a
structured debug file containing master-slave relationships, cycle count, state and signal details,
then compares that file against the protocol state machine and timing signals the integrator
extracted earlier.

**[FROM PAPER] The worked example (Fig. 5).** Master, bridge and slave are interconnected. The master
is stuck in SEND. Its valid signal reaches the bridge and triggers the bridge's ready, which is fed
back — but the master's input ready fails to trigger. Comparing the debug file against the protocol
FSM locates the fault: the trigger for `s_axi_wready` was mistakenly placed in the `WR_DATA` state and
is repositioned to `WR_ADDR`. The paper calls erroneous association of state-triggered signals with
incorrect states a typical issue.

**[INFERENCE]** This is the paper's most transferable idea, and the reason it works is a reframing
rather than a modelling advance. Reading a waveform is a perception task over continuous,
high-volume, weakly-structured data. Comparing observed transitions against specified transitions is
a symbolic task over small structured data — and language models are far more reliable at the second.
The technique is not specific to SoC generation.

**[INFERENCE]** Note also why the example bug is well chosen: every module is individually correct.
The fault is a *relationship*, invisible without comparing behaviour against the protocol's state
machine.

**[NOT SPECIFIED]** Iteration counts; behaviour when the loop fails to converge; verification
coverage; the debug file schema.

### 3.4 Cross-cutting mechanisms (Section III)

**[FROM PAPER]**

- Pre-defined behavioural guidelines and detailed prompts prevent deviation during reasoning. One
  example given in prose: the IP library manager must finish processing all IP information before
  moving on.
- A hierarchical RAG method: agents first identify IP types, then retrieve details.
- Because compilation and simulation tools lack suitable APIs, commands are encapsulated in scripts.
  Agents adapt and execute them, storing outputs in specific locations for other agents.
- Agents observe the actions of their predecessors, enabling smooth collaboration.

**[INFERENCE] A structural risk in the handoff.** The protocol FSM and timing rules extracted by the
integrator are used both to *build* the adapters and to *judge* them. An extraction error is
therefore invisible to the check — both build and check would be wrong in the same direction. An
independent source of protocol truth (a formal AXI property set, say) would catch it. The paper does
not describe one.

## 4. Evaluation

### 4.1 Setup (Section V-A)

**[FROM PAPER]** MetaGPT as the agent framework; DeepSeek-Reasoner per agent; Synopsys VCS for
functional verification; Cadence Genus and Innovus for synthesis and backend; commercial TSMC 22 nm;
a commercial SRAM compiler; an in-house simulator for chip performance. Baselines: Chipyard, LiteX,
ESP, plus PULP Snitch for the homogeneous comparison.

**[INFERENCE]** The two halves are not equally reachable. The generation-and-verification loop could
in principle be attempted with a DeepSeek API key, MetaGPT and an open simulator. The evaluation half
cannot: Genus, Innovus, the SRAM compiler and the 22 nm PDK all require commercial licences, and the
PDK an NDA. Table III cannot be independently checked without that access.

### 4.2 The two designs (Table III)

| Feature | Case A | Case B |
|---|---|---|
| PDK | TSMC 22 nm | TSMC 22 nm |
| Target | Edge AI | General mobile |
| Frequency | 500 MHz | 1 GHz |
| Total power | 332.4 mW | 16.23 W |
| Total area | 4 mm² | 27.03 mm² |

Case A: CVA6 + NVDLA + DSP. Case B: dual-core Xiangshan + Ventus GPU + Gemmini NPU + H.264/H.265
encoder + encryption unit + DDR4 controller. Post-place-and-route results; neither was manufactured.

### 4.3 Framework comparison (Table II)

| Framework | CPUs | DSA | I/O | SoC combinations | Interaction | Extensibility |
|---|---:|---:|---|---:|---|---|
| Chipyard | 4 | 3 | Few | 16 | Chisel | Hard |
| LiteX | 19 | 0 | Many | 19 | Python | Hard |
| ESP | 3 | 1 | Few | 6 | GUI | Middle |
| GenSoC | 23 | 26 | Numerous | 598 | Natural language | Easy |

**[INFERENCE]** Two columns are counts; the rest are the authors' own labels. "Extensibility:
Hard/Middle/Easy" and "I/O: Few/Many/Numerous" are judgements made by the authors of the framework
being favourably compared, with no stated rubric. The counts are checkable in principle; the
qualitative columns are not, and should not be read as a neutral benchmark of framework quality.

**[NOT SPECIFIED]** The formula behind 598 configuration schemes, and how many of those combinations
have actually been generated and verified. Reachable and validated are different claims.

### 4.4 Normalized energy cost (Fig. 7)

Every group is normalised to the GenSoC case, so GenSoC is 1 by construction.

| Scenario | LiteX | Chipyard | ESP | GenSoC |
|---|---:|---:|---:|---:|
| Object detection (Case A) | 27.18× | 5.12× | 3.48× | 1× |
| Speech recognition (Case A) | 24.45× | 2.82× | 3.73× | 1× |
| AI assistant (Case B) | 29.67× | 9.82× | 13.48× | 1× |
| Augmented reality (Case B) | 24.45× | 7.36× | 4.94× | 1× |

**[BACKGROUND]** These are ratios, not joules. The paper reports no absolute energy for these
scenarios, so the figures support "A used N times less than B" and nothing about battery life or
watt-hours.

**[FROM PAPER]** The mechanism, stated by the paper: LiteX's disparity primarily stems from its lack
of a DSA module, forcing all workloads onto the CPU. Case A's efficiency is largely attributed to its
DSP; Case B's predominantly to its GPU.

**[FROM PAPER]** What each framework generated for Case A: LiteX → CVA6; ESP → CVA6 + NVDLA;
Chipyard → Rocket + Gemmini; GenSoC → CVA6 + NVDLA + DSP.

**[INFERENCE]** Read those two together and the result becomes much more specific than the headline.
ESP generated the *same CPU and same NPU* as Case A and sits at 3.48× — essentially all of which is
the DSP. So the comparison is largely measuring the value of adding a DSP to an edge-AI chip. That is
a real and useful finding, and it is not the same as measuring the quality of the generator.

### 4.5 Heterogeneous vs homogeneous (Fig. 8)

| Case | Scenario | Baseline | Gain |
|---|---|---|---:|
| A | Object detection | Snitch A | 2.13× |
| A | Speech recognition | Snitch A | 2.27× |
| B | AI assistant | Snitch B | 2.46× |
| B | Augmented reality | Snitch B | 2.79× |

**[INFERENCE]** This is the more defensible of the two energy comparisons, because the baselines are
area-matched. The confound that dominates Fig. 7 is exactly what is being measured here, deliberately
and with a controlled budget. A 2–2.8× advantage from specialisation is also a modest, credible
number rather than a spectacular one.

### 4.6 Development time (Section V-C)

**[FROM PAPER]** Three graduate students manually completed the IP integration and verification,
averaging about four hours; the framework accomplished the same task in minutes, reported as >24×
faster. The most time-consuming phase for the students was verification, because manually written
code often contained bugs. Their time also included reading and locating the specific interfaces,
then writing the interface adapter.

**[INFERENCE]** Directionally believable, quantitatively soft. Three participants, one task, no
reported experience level or variance, no GenSoC runtime distribution to compare against, and no
statement of how many GenSoC attempts preceded the successful run. The informative part is the
qualitative one the paper supplies: verification dominated the manual effort, which is precisely the
loop being automated.

## 5. What is novel

1. A multi-agent division of labour for whole-SoC generation, rather than single-module code
   generation.
2. A multi-level description method for open-source IP.
3. Natural-language-driven IP selection with explicit hard/soft constraint reasoning.
4. Protocol-driven integration: extract structured protocol knowledge first, then integrate against
   it.
5. Adapter generation as a fallback rather than a default.
6. **State-machine signal comparison for verification.** The genuinely novel piece.
7. Demonstration on two heterogeneous SoCs carried through to place and route.

**[INFERENCE]** If only one idea transfers, it is number 6.

## 6. Limitations

| # | Limitation | Assessment |
|---|---|---|
| 1 | **Commercial tool dependency** | VCS, Genus, Innovus, a commercial SRAM compiler and the TSMC 22 nm PDK. The functional-verification loop could be approximated with open tools; the physical-design numbers cannot be reproduced at all without the same licensed flow. **[FROM PAPER]** |
| 2 | **IP library availability** | **[NOT SPECIFIED]** No release, licence or repository is stated for the refined 90+ IP library. Since it is the foundation resource the whole method depends on, this materially limits reproducibility. |
| 3 | **Agent configuration** | **[NOT SPECIFIED]** No prompt text, tool script or MetaGPT role definition appears in the paper. |
| 4 | **Reliability** | **[INFERENCE]** Passing a testbench is not a proof. Nothing is reported about coverage, corner cases, clock-domain crossings, power intent, or timing across corners. No failure or non-convergence cases are reported. |
| 5 | **Evaluation scale** | **[INFERENCE]** Two SoCs, four scenarios, three human participants. Enough to demonstrate the method end to end; not enough to establish how it behaves across many designs. No success rate over repeated runs. |
| 6 | **Fairness of comparison** | **[INFERENCE]** The energy comparison largely measures architecture rather than the generator. See §4.4. |
| 7 | **The time study** | **[INFERENCE]** Illustrative, not controlled. See §4.6. |
| 8 | **598 combinations** | **[NOT SPECIFIED]** Counting method and validation status both unstated. |

### Where scepticism is *not* warranted

**[INFERENCE]** Two design cases were carried through synthesis and place-and-route in a commercial
22 nm process, with post-P&R power, area and frequency reported. That is not a result one gets by
accident or by an LLM producing plausible-looking output — a design that does not elaborate does not
route, and one that does not meet timing does not report a frequency. Whatever share of the work
involved human intervention, two complete heterogeneous SoCs exist at the end of it. Case B in
particular — six block types including a DDR4 controller, at 1 GHz and 27 mm² — is a substantial
systems result and the hardest part of the paper to fake.

## 7. What to take, what to hold back

**Take from it**

- The multi-agent decomposition, and the artifacts that connect the agents
- The three-level IP description as an index built for retrieval
- Separating hard-constraint elimination from soft-constraint ranking
- Extracting protocol rules into machine-checkable form *before* generating anything
- State-machine signal comparison as a verification technique

**Hold back on**

- The 27.18× / 29.67× figures as evidence about the generator specifically
- The >24× speedup as a measured constant
- The 598 combinations as validated designs
- Any assumption that the method is reproducible today
- Reading "verified" as anything stronger than "passed the tests that were written"

---

## 8. The comparison the paper does not run

**[INFERENCE]** The most informative missing experiment is the obvious one: take the same three
baseline frameworks, have an experienced human configure each with the best architecture it can
express for the workload, and compare against GenSoC's output. That would separate "GenSoC chose a
good architecture" from "GenSoC integrates faster than a person can". Both are worthwhile claims; the
current evaluation blends them.

Other questions a follow-up would need to answer:

- Is the refined IP library released, and under what licence?
- Are the agent prompts, guidelines and tool scripts released?
- What is the success rate over repeated generation runs?
- How many validator iterations does a typical case need, and what happens when it does not converge?
- What verification coverage do the generated testbenches achieve?
